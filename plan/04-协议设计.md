# 04 · 协议设计

> 状态：已评审（2026-10-27）
> 上游：[01-系统架构设计.md](01-系统架构设计.md)、[03-规则族设计.md](03-规则族设计.md)
> 本文是**接口路径、字段、错误码的唯一权威**。
> 命名约定：**协议字段与 JSON 内容一律 `snake_case`**；数据库列名为 `camelCase`（contentHub 风格），由 `processor` 层做映射。

## 1. 基础约定

| 项 | 约定 |
| --- | --- |
| 基地址 | 同源 `/api`；WebSocket `/ws` |
| 编码 | UTF-8，`Content-Type: application/json` |
| 认证 | REST：`Authorization: Bearer <JWT>`；WS：`?token=<JWT>` |
| 时间 | REST 输出 ISO 8601 带 `+08:00`；WS 倒计时用 epoch 秒（float） |
| ID | 用户标识统一 `login_id`（string）；资源用 `recID`（int）或业务码（`room_code`、`family_code`、`template_code`、`skin_code`） |
| 分页 | `limit`（默认 20，最大 100；战绩与审计列表默认 30）+ `before_id`（游标，不含） |
| 错误体 | `{"detail": "中文提示", "code": "ERROR_CODE"}` |
| 幂等 | 创建类接口支持业务唯一键；重复提交返回既有资源而非 500 |
| 协议版本 | WS 信封 `v=2`（本版破坏性变更见 §8） |

约定：

- `login_id` 兼容旧字段 `username`（仅登录接口，收到 `username` 时按 `login_id` 处理），便于过渡。
- 登录成功后由服务端写 `mj_user_pref.lastFamilyID`（若为空且仅有一个家庭则自动选中）。
- 口令只透传账号服务，服务端与日志均不落明文；`passwd` 字段不入日志、不回显（哈希口径见 §2.4）。
- 前端**不硬编码**注册/找回开关，一律读 `GET /api/auth/options`。

### 2.1 注册

两步：先发验证码，再提交注册。参考实现见 `museum/webserver` 的 `Register.vue`（`/smsrequest` + `/registration`），本项目把两步收敛到同一后端。

| # | 方法 路径 | 请求 | 响应 | 权限 |
| --- | --- | --- | --- | --- |
| 42 | `POST /api/auth/verify-code` | `{login_id, scene:"register"}` | `{ok:true, cooldown_seconds, expire_seconds}` | 公开（限流） |
| 2 | `POST /api/auth/register` | `{login_id, passwd, verify_code, nick_name?}` | `{ok:true, login_id}` | 公开（开关 + 已发码） |

请求与响应示例：

```json
// POST /api/auth/verify-code
{"login_id":"13800000000","scene":"register"}
→ {"ok":true,"cooldown_seconds":60,"expire_seconds":600}

// POST /api/auth/register
{"login_id":"13800000000","passwd":"<明文口令>","verify_code":"123456","nick_name":"爸爸"}
→ {"ok":true,"login_id":"13800000000"}
```

校验规则（前端与服务端同规则，服务端为准）：

| 字段 | 规则 | 失败提示 |
| --- | --- | --- |
| `login_id` | `^1[3-9]\d{9}$`（11 位手机号，账号服务以手机号作登录号） | 「请输入正确的手机号」 |
| `passwd` | 长度 6–32，不允许空白字符；不做复杂度强制 | 「密码长度不能少于 6 位」 |
| `verify_code` | `^\d{6}$`，必填 | 「请输入 6 位数字验证码」 |
| `nick_name` | 可选，1–20 字，缺省取 `login_id` | 「昵称最多 20 字」 |
| 确认口令 | 仅前端校验，两次一致 | 「两次输入的密码不一致」 |
| 服务条款 | 仅前端强制勾选 | 「请先同意服务条款」 |

服务端流程：

1. `ACCOUNT_ALLOW_REGISTER=false` → 403 `ACCOUNT_REGISTER_DISABLED`（不触达账号服务）。
2. 格式校验 → 400 `ACCOUNT_LOGIN_ID_INVALID` / `PASSWORD_TOO_SHORT`。
3. `verify_code` 为空或非 6 位数字 → 400 `VERIFY_CODE_REQUIRED`。
4. 调账号服务 `A0A0`，请求带 `loginID`、`passwd = md5(passwd + login_id)`、`verifyCode`、`nickName`；账号服务校验验证码并建号。
5. 成功后立即 `A3A0` 取资料 → `syncUserBasic`（insert，写 `regID/regYMDHMS`、`regPosition="web"`）。
6. **不签发 JWT**：返回 `{ok:true, login_id}`，前端跳 `/login` 并预填账号。理由与 museum 一致——账号服务注册回包不含会话，避免「注册了一半却已登录」的中间态。
7. 审计：记录 `login_id`、来源 IP、UA、结果，**不记验证码**。

### 2.2 找回口令（忘记密码）

两步：验证账号发码 → 凭码设新口令。不需要登录态，**不产生会话**。参考实现见 `museum/webserver` 的 `ForgotPassword.vue`（`/smsrequest` + `/resetpasswd`，两步在同一页面用 `step` 切换）。

| # | 方法 路径 | 请求 | 响应 | 权限 |
| --- | --- | --- | --- | --- |
| 42 | `POST /api/auth/verify-code` | `{login_id, scene:"reset_password"}` | `{ok:true, cooldown_seconds, expire_seconds}` | 公开（限流） |
| 43 | `POST /api/auth/password/reset` | `{login_id, verify_code, new_passwd}` | `{ok:true}` | 公开（开关 + 已发码） |

```json
// 第一步
{"login_id":"13800000000","scene":"reset_password"}
→ {"ok":true,"cooldown_seconds":60,"expire_seconds":600}

// 第二步
{"login_id":"13800000000","verify_code":"123456","new_passwd":"<新明文口令>"}
→ {"ok":true}
```

流程与约束：

1. `ACCOUNT_ALLOW_PASSWORD_RESET=false` → 403 `PASSWORD_RESET_DISABLED`。
2. 第一步**不校验账号是否存在**：账号服务回 `B1`/`BW` 时对外仍返回 `{ok:true}`，只在审计日志记原因，避免手机号枚举。
3. 第二步调账号服务 `A9A0`，带 `loginID`、`passwd = md5(new_passwd + login_id)`、`verifyCode`；验证码由账号服务一次性校验（校验通过即作废）。
4. 成功后 `A3A0` 同步档案镜像，更新 `USER_BASIC.passwdYMDHMS`；**不签 JWT、不清除他人会话**（本轮不做全局会话吊销，列入后续迭代）。
5. 验证码失败一律 `VERIFY_CODE_INVALID`（不区分「账号不存在 / 验证码错 / 验证码过期」），本地失败计数 +1，达阈值返回 `VERIFY_CODE_ATTEMPTS_EXCEEDED`。
6. 新口令不得与旧口令相同：由账号服务判定（`B6`）并映射为 `PASSWORD_REUSED`；本地不缓存旧口令，不做预校验。

### 2.3 验证码策略

| 项 | 约定 |
| --- | --- |
| 生成与存储 | 全部在账号服务（acis）侧，本地**不建表、不落 Redis、不缓存明文** |
| 有效期 | 10 分钟（账号服务 TTL；`expire_seconds` 回传前端仅用于文案） |
| 重发间隔 | 60 秒（本地冷却 + 账号服务 `CS` 兜底），冷却按 `login_id` 计，不因刷新页面重置 |
| 错误次数 | 同一 `login_id` 连续 5 次失败后作废本次验证码，必须重新获取（`AUTH_VERIFY_CODE_MAX_ATTEMPTS`） |
| 一次性 | 校验通过即失效；不提供「先校验后提交」的两段式接口，避免同一码复用 |
| `scene` | `register` / `reset_password`，仅用于本地限流分桶、审计与前端文案；账号服务侧不区分 |
| 日志 | 验证码、口令明文、`md5` 结果均不得进日志、审计详情或错误响应 |
| 限流实现 | 单进程内存计数器（`--workers 1`），重启清零；不做跨实例共享 |

不做的事：图形验证码、第三方登录、记住我（与 museum 现状一致，本轮不引入）。

### 2.4 口令与传输

1. 前端一律提交**明文口令**（HTTPS/WSS 已覆盖），**不在前端做 md5**。museum 的前端用 `md5(pwd + loginID)` 作为等价口令，该值一旦落到 `localStorage`/日志即成为可重放凭据，与本项目「口令只透传账号服务」的约束冲突。
2. 服务端在 `processor/accountService` 内统一计算 `md5(passwd + login_id)` 后再调 acis（与 contentHub 既有算法一致），明文只存在于请求内存，不落日志、不进 JWT、不回显。
3. 登录、注册、改密、找回口令**共用同一哈希口径**，保证「注册 → 登录」「重置 → 登录」一致。
4. `USER_BASIC.passwd` 仍只做镜像，不参与任何校验（见 [01 §5.5](01-系统架构设计.md)、[02 §3.1](02-数据库设计.md)）。
5. 口令强度只做长度约束：账号服务侧为唯一权威，前端不重复实现复杂度规则，避免两端提示不一致。

### 2.5 与账号服务（acis）的映射

| 场景 | 端点 | acis CMD | 关键字段 |
| --- | --- | --- | --- |
| 登录 | `POST /api/auth/login` | `A0A0` | `loginID`、`passwd`（md5） |
| 注册 | `POST /api/auth/register` | `A0A0` | 同上 + `verifyCode`、`nickName` |
| 发验证码 | `POST /api/auth/verify-code` | `A6A0` | `loginID`、`lang` |
| 找回口令 | `POST /api/auth/password/reset` | `A9A0` | `loginID`、`passwd`（md5）、`verifyCode` |
| 登录态改密 | `POST /api/auth/password` | `A9A0` | `sessionID`、`loginID`、`passwd`（md5） |
| 取资料 | 内部 | `A3A0` | `loginID` |
| 登出 | `POST /api/auth/logout` | `A5A0` | `sessionID` |

`A7A0`（独立校验验证码）**不启用**：验证码一次性，单独校验后仍要再提交一次，等于扩大重放窗口。

acis `errCode` → 本系统错误码：

| acis | 本系统 `code` | 场景 |
| --- | --- | --- |
| `B0` | —（成功） | 全部 |
| `B1` | `ACCOUNT_AUTH_FAILED`（登录）/ 发码步骤对外隐藏 | 账号不存在 |
| `B3`/`B5` | `ACCOUNT_AUTH_FAILED` | 口令错 |
| `B4` | `ACCOUNT_LOGIN_ID_EXISTS` | 注册重复 |
| `B6` | `PASSWORD_REUSED` | 新口令与旧口令相同 |
| `B7` | `ACCOUNT_LOGIN_ID_INVALID` | 登录号无效 |
| `B8` | `UNAUTHORIZED` | 会话失效 |
| `BA` | `BAD_REQUEST` | 数据格式 |
| `BE`/`BS` | `ACCOUNT_REGISTER_DISABLED` | 账号服务不允许注册 |
| `BM` | `VERIFY_CODE_INVALID` | 验证码无效/过期/已用 |
| `BN` | `VERIFY_CODE_SEND_FAILED` | 短信发送失败 |
| `BW` | 发码步骤对外隐藏；注册步骤 `ACCOUNT_LOGIN_ID_INVALID` | 手机号错误 |
| `CS` | `VERIFY_CODE_SEND_TOO_FAST` | 发送过频 |
| `CI` | `ACCOUNT_SERVICE_UNAVAILABLE`（503） | 账号服务不可达 |

## 3. 家庭与成员

| # | 方法 路径 | 请求 | 响应 | 权限 |
| --- | --- | --- | --- | --- |
| 7 | `GET /api/families` | — | `families[]` | 登录 |
| 8 | `POST /api/families` | `{family_code?, family_name}` | `family` | 登录 |
| 9 | `GET /api/families/{family_code}` | — | `family` | 成员 |
| 10 | `PATCH /api/families/{family_code}` | `{family_name?, default_rule_family_code?, default_skin_code?}` | `family` | owner/admin |
| 11 | `GET /api/families/{family_code}/members` | — | `members[]` | 成员 |
| 12 | `POST /api/families/{family_code}/members` | `{login_id, member_role}` | `member` | owner/admin |
| 13 | `PATCH /api/families/{family_code}/members/{login_id}` | `{member_role?, member_status?}` | `member` | owner/admin |
| 14 | `DELETE /api/families/{family_code}/members/{login_id}` | — | `{ok:true}` | owner/admin |

```json
// family
{
  "family_code": "lianjia",
  "family_name": "廉家",
  "owner_login_id": "13800000000",
  "default_rule_family_code": "baishi",
  "default_skin_code": "css-classic",
  "member_role": "OWNER",          // 当前用户的角色
  "status": "ENABLED",
  "sort_order": 0
}
// member
{"login_id":"13900000000","nick_name":"妈妈","member_role":"MEMBER","member_status":"ACTIVE","joined_ymdhms":"20261025193000"}
```

规则：

- `family_code`：`^[a-z][a-z0-9_]{1,31}$`；不传则按 `family_name` 生成拼音/随机后缀，冲突重试。
- 创建家庭：创建者自动写 `mj_family_member(OWNER)` 与 `mj_user_pref.lastFamilyID`。
- 成员必须已存在于账号服务（AIA0 校验）；添加时若 `USER_BASIC` 无档案，先 A3A0 同步。
- 不能移除 owner；owner 转让走 `PATCH` 将目标设为 `OWNER`，原 owner 降为 `ADMIN`（同一事务）。
- 家庭停用后：成员仍可登录，但房间/模板/皮肤接口返回 `FAMILY_DISABLED`。

## 4. 用户偏好

| # | 方法 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| 15 | `GET /api/user/pref` | — | `{last_family_code, skin_code, sound_enabled, sound_volume, chat_sound, show_tenpai}` |
| 16 | `PUT /api/user/pref` | `{last_family_code?, skin_code?, sound_enabled?, sound_volume?, chat_sound?, show_tenpai?}` | 同上 |

- `last_family_code` 必须是当前用户所属家庭，否则 403。
- `skin_code` 必须对当前家庭可见（全局或本家庭），否则 400；传空串表示回到默认。
- `sound_enabled` / `chat_sound` / `show_tenpai` 为布尔；`sound_volume` 为 0–100 整数，越界返回 400 `SOUND_VOLUME_INVALID`；缺省 `sound_enabled=true`、`sound_volume=70`、`chat_sound=true`。
- 音效纯前端播放，此接口只负责持久化偏好；**没有任何 BGM 字段**（见 [08-音效设计](08-音效设计.md)）。

- `ready` 不是表字段：由 `game/families/registry.py` 的导入期自检结果拼出（引擎已注册 + capability 可解析 + patterns 已注册 + tile_set 可建墙）；`ready=false` 的族可列模板，但开桌返回 `RULE_FAMILY_NOT_READY`（见 [02 §3.5](02-数据库设计.md)）。

- `config` 的字段与校验见 `03-规则族设计.md`；服务端按 `rule_family_code` 的能力声明校验，未知字段直接 400（`extra=forbid`）。
- `validate` 不落库；`summary` 为可直接展示的一句话（如「底分 1 · 2 的 N 次方 · 封顶 8 番 · 可吃 · 限时 15 秒」）。

- 邀请码：`^[1-9][0-9]{5}$`，全局唯一；生成用加密随机源（`secrets.randbelow(900000)+100000`），冲突重试 10 次，耗尽返回 `ROOM_CODE_EXHAUSTED`。
- `spectate.viewer_counts` 按座位 0–3 给出当前围观人数（仅家庭成员可见的汇总，不含观战者身份）；`available=false` 表示 4×10 已满，入房后无法观战（WS 握手返回 `ROOM_SPECTATE_FULL`）。实时值以 `room.welcome` 与 `event.spectate_changed` 为准。
- 入房：先按 `room_code` 查房 → 校验房间所属家庭可用（停用返回 `FAMILY_DISABLED`）→ 校验 `status=OPEN`。**邀请码即入场凭证**：非本家庭的登录用户同样可以入房（#28 与 WS 握手），但拿不到该家庭的管理员身份；房间列表（#26）、房间详情/聊天（#27/#30）与开桌（#25）仍限本家庭成员——按自增 `room_id` 放开会让人枚举出邀请码。
- 战绩归属房间所在家庭（见 §7），但**参与者本人**的「我的场次」跨家庭可见：客队玩家会在自己列表里看到该场（带 `family_code` 标记为客队场次）。
- `template_id` 必须是该家庭可见（`familyID ∈ {0, 家庭}`）且 `active_flag=1`；族必须 `ready=true`（柏氏细则未定时不可开桌）。

```json
{"skin_code":"lianjia-jade","skin_name":"廉家青玉","family_code":"lianjia",
 "is_default":true,"status":"ENABLED","tile_aspect":0.6667,"asset_count":35,

 "assets":{"1m":"/majiangapp/tiles/lianjia-jade/1m.8f3a1c.webp","back":"/majiangapp/tiles/lianjia-jade/back.2b9d40.webp"},

```

规则：

- 上传校验：扩展名与 magic number 双白名单（`png`/`webp`）；单文件 ≤ 512 KB；尺寸建议 96×144（2× 为 192×288），宽高比 2:3；文件名由服务端生成，不接受用户输入。
- 发布条件：34 张牌 + `back` 共 35 个 `tile_key` 齐全才能 `status=ENABLED`；缺项返回 `SKIN_ASSET_INCOMPLETE` 并列出缺失键。
- `tile_key` 取值见 `05-UI设计.md` §6；不允许自定义键。
- 新建（#37）后为 `status=DISABLED`；发布即 `PATCH /api/skins/{skin_code}` 传 `{"status":"ENABLED"}`（与 #40 同一入口，完整性校验相同）。
- `preview` 不是 `tile_key`：`PUT/DELETE .../preview` 只写 `mj_tile_skin.previewFileID`，不进 `assets`、不计入 `asset_count`；清单里通过 `preview_url` 给出。
- 默认皮肤：同家庭只能有一个 `is_default=true`；设置时同事务清掉旧的。家庭自有皮肤设默认后，全局内置皮肤在**该家庭**清单里的 `is_default` 显示为 `false`（内置行的 `defaultFlag` 不被改写，避免影响其他家庭）。
- 删除：软删（`delFlag=1`），不影响正在使用的客户端缓存；物理文件延迟清理。删除单张资源后皮肤仍保持 ENABLED，该张由前端回退 CSS（`05 §9.3`）。
- `GET /api/skins` 支持 `If-None-Match`，返回 `ETag`（按家庭 + `updated_at` 计算）。

## 9. WebSocket

### 9.1 连接

```
ws(s)://<host>/ws?token=<JWT>&code=<6位数字邀请码>
```

握手失败：

| 场景 | 消息 | 关闭码 |
| --- | --- | --- |
| token 无效/过期 | `error{UNAUTHORIZED}` | 4001 |
| 邀请码格式错误/房间不存在/已关闭 | `error{ROOM_NOT_FOUND}` | 4004 |
| 房间所属家庭已停用 | `error{FAMILY_DISABLED}` | 4003 |
| 协议版本不匹配 | `error{BAD_VERSION}` | 4002 |
| 座位已满且观战位已满（4×10） | `error{ROOM_SPECTATE_FULL}` | 4005 |

> `ROOM_FULL` 非致命：座位满但仍有观战名额时连接保持，客户端进入观战选择器；`ROOM_SPECTATE_FULL` 才断开连接。
>
> 入房鉴权：邀请码即入场凭证，**非本家庭的登录用户同样可以握手进桌**（不再返回 `NOT_FAMILY_MEMBER`）；只有房间所属家庭被停用时才整房拒绝。

### 9.2 信封（v2）

```json
{"v":2,"type":"event.discarded","ts":1792900000,"data":{"seat":2,"tile":15}}
```

- `v`：固定 `2`；服务端收到 `v!=2` 直接 `BAD_VERSION`。
- `seq`：客户端上行可选；服务端不回。
- `ts`：服务端 epoch 秒。

### 9.3 客户端 → 服务端

| type | data | 说明 |
| --- | --- | --- |
| `ping` | — | 心跳，回 `pong` |
| `state.resync` | — | 请求全量快照 |
| `spectate.target` | `{seat}` 或 `{seat:null}` | 选择/切换唯一观战对象；`null` 取消跟随；仅无座位者可用 |
| `seat.ready` | — | 准备/取消准备 |
| `game.start` | — | 房主开桌，需 4 人且全部准备 |
| `game.next` | — | 房主开始下一局 |
| `game.action` | `{action, tiles?, kong_kind?}` | 见下 |
| `room.pause` | `{note?}` | 暂停；任一在座玩家可发（`capability.switches` 含 `pause` 才可用） |
| `room.resume` | — | 恢复；任一在座玩家可发 |
| `chat.send` | `{content}` | 1–200 字，5 秒最多 3 条 |

```json
{"action":"discard","tiles":[15]}
{"action":"chow","tiles":[13,14]}
{"action":"pong","tiles":[15]}
{"action":"kong","tiles":[15],"kong_kind":"hidden"}
{"action":"hu"}
{"action":"pass"}
```

- 牌编码 0–33：0–8 万、9–17 筒、18–26 条、27–30 东南西北、31–33 中发白。
- 四川族无字牌，服务端拒绝 27–33。
- 观战：`seat` 为目标**当前座位**（0–3）；服务端按目标 `loginID` 建立绑定，抽座换座后自动跟随同一人。同一观战者只保留 1 条绑定（`loginID` 维度），切换即把名额从旧目标转移到新目标；目标座位无人返回 `SPECTATE_TARGET_INVALID`；目标已有 10 人围观返回 `SPECTATE_TARGET_FULL` 且保持原目标不变；在座玩家发此消息返回 `SPECTATE_NOT_ALLOWED`；同一 `seat` 重复提交幂等。
- 动作幂等：重复提交返回当前状态，不报错。
- `game.start`：4 人全部准备后由房主触发；服务端先抽座（广播 `event.seats_drawn`）再发牌。抽座只在每圈首局发生，圈内 `game.next` 不重抽。
- `game.next`：仅在 `phase=settled` 或荒庄后可发；**无杠重发由服务端自动进行**，客户端只需接收 `event.round_restarted`，不需再发 `game.next`。
- 杠与抢杠：只有 `kong_kind=exposed`（明杠）声明后开 `event.claim_open{reason:"rob_kong"}` 窗口；窗口内有人 `hu` 则杠作废、按抢杠胡结算（不发 `event.kongged`，且不计杠分）；无人抢才发 `event.kongged` 并补牌。`added`（补杠）与 `hidden`（暗杠）**直接成立**：发 `event.kongged`、计杠分、开补牌，不产生抢杠询问。

```json

            "family_code":"lianjia","family_name":"廉家",

              "kong_score":{"enabled":true,"exposed":1,"hidden":2,"added":1},
              "ting_hint":true,"patterns":["标准胡","七对"],"rounds_per_game":4}},
  "self_seat": 3,
  "spectate": null,

    {"seat":0,"login_id":"138...","display_name":"爸爸","color":"#C9A063",
     "ready":true,"connected":true,"is_host":true,"hand_count":13,
     "wind":0,"is_dealer":true,"spectator_count":2,
     "melds":[{"kind":"pong","kind_name":"碰","tiles":[15,15,15],"count":3,"from_seat":2}],
     "round_score":0,"total_score":128}
  ],
  "status":"playing",
  "paused":{"paused":false,"by_seat":null,"note":null},
  "round_no":1,
  "dealer_seat":0,
  "round_wind":0,
  "game_total_rounds":4,
  "hand":[0,0,2,4,8,9,11,15,18,20,24,27,33],
  "drawn":33,
  "turn":0,
  "phase":"discard",
  "wall_count":83,
  "discards":[[],[],[],[]],
  "last_discard":{"seat":2,"tile":15},
  "legal":{"actions":[{"action":"discard"}],"claim_tile":null,"claim_from":null,"reason":null},
  "tenpai":{},
  "deadline":1792900123.4,
  "claim_deadline":null,
  "result":null

```

约定：

- `hand` 对 `self_seat`（在座本人）或 `spectate.target_seat`（观战目标）填充；其余座位只有 `hand_count`；暗杠对非本人且非目标只给 `count=4` 的空 `tiles`。
- `drawn` 仅当该连接是本人或观战目标、且其刚摸牌时非空。
- `spectate`：在座玩家为 `null`；观战者已选目标时为 `{target_seat,target_login_id,viewer_count,limit_per_seat}`；未选目标为 `null`，此时 `hand=[]`、`drawn=null`、`legal.actions=[]`，只收公共状态。
- `legal.actions` 元素可带 `kong_kind`、`tiles`、`label`（如「暗杠五万」）；观战者恒为空数组。
- `tenpai` 仅 `ting_hint=true` 且 `phase=discard` 且轮到本人或观战目标时下发，格式 `{"<打出的牌>": [等待的牌]}`。
- `deadline` 仅 `turn_timeout.enabled=true` 且 `phase=discard`；`claim_deadline` 仅询问窗口开放时；观战者只读展示，不可操作。
- `seats[].spectator_count` 为该座位当前围观人数（0–10），全房可见、不含观战者身份。
- `paused.paused=true` 时 `legal.actions` 恒为空、`deadline` 与 `claim_deadline` 为 `null`；恢复后按暂停前剩余时间重算，不做补偿。
- `result` 为最近一次结算（`round_no`、`winners`、`fan_raw`、`fan_cap`、`multipliers`、`score_delta`、`kong_delta`、`payer_allocation`、`is_last_round`）。
- `seats[].wind`：0–3 对应**本局门风**（庄家恒为 0=东），由 `(seat - dealer_seat) % 4` 推出，前端据此显示各家的风；`seats[].is_dealer` 与 `seat == dealer_seat` 等价，冗余供 UI 直接渲染。
- `round_wind`：本局局风 = `round_no - 1`（0 东、1 南、2 西、3 北），**与谁坐庄无关**；前端据此显示「东风局/南风局」与「第 x/4 局」。
- 抽座结果只在 `event.seats_drawn` 广播一次；重连靠 `seats[].wind` 恢复，不重放骰子。
- 荒庄（有杠）走 `event.settled{is_draw:true}`；无杠重发走 `event.round_restarted`，二者都不产生 `event.game_finished`。
- 新增字段一律可选；前端不得因缺字段崩溃。

```json
 "hand":[0,0,2,4,8,9,11,15,18,20,24,27],
 "drawn":33,
 "legal":{"actions":[]}}
```

## 11. 兼容与破坏性变更

| 变更 | 影响 | 处理 |
| --- | --- | --- |
| `user_id`（int）→ `login_id`（string） | 快照、聊天、历史、成员接口 | 协议升 `v=2`；前后端同版本发布 |
| 登录参数 `username` → `login_id` | 登录接口 | 服务端兼容 `username` 别名 |
| 规则配置字段改为 `snake_case` + 族能力约束 | 规则页 | 前端按 `capability` 渲染 |
| `event.settled` 增加 `winners` 数组 | 结算展示 | 单赢家时长度 1；旧字段 `winner_seat` 保留为 `winners[0].seat` |
| 邀请码由字母数字 → 6 位数字 | 入房 | 前端输入框改为数字键盘；旧码全部失效（不迁移旧数据） |
| 新增 `family_code` 参数 | 房间/模板/皮肤列表 | 缺省取 `last_family_code` |
| `event.settled` 增 `fan_raw`/`multipliers`/`payer_allocation`/`kong_delta` | 结算展示 | 均可选，旧前端忽略；柏氏必须展示倍数与包牌 |
| 快照增 `paused` | 牌桌 | 缺省 `{paused:false,...}`，旧前端忽略 |
| 新增 `room.pause`/`room.resume`/`event.paused` | 牌桌 | 仅 `capability.switches` 含 `pause` 的族可用 |
| 新增 `spectate.target`/`event.spectate_changed`、快照 `spectate` 与 `seats[].spectator_count` | 牌桌观战 | 均为增量字段，旧前端忽略后降级为「无手牌只读视角」 |
| `ROOM_FULL` 语义收窄，新增 `ROOM_SPECTATE_FULL` | 满座入房 | 满座但仍有观战名额仍返回 `ROOM_FULL`（非致命）；4×10 满才返回 `ROOM_SPECTATE_FULL`（4005） |
| 协议 `v=1` 不再支持 | 旧前端 | 前端同版本发布；服务端 `BAD_VERSION` 快速失败 |
| `POST /api/auth/register` 增 `verify_code`（必填） | 注册 | 前端同版本发布；服务端对缺字段返回 `VERIFY_CODE_REQUIRED` |
| 新增 `verify-code` / `password/reset` / `options` | 登录页 | 老前端无入口、无影响；`options` 缺省按「注册关、找回开」降级 |

## 12. 验收清单

1. 所有接口在 `04` 与 `02/03` 的字段名一致（`login_id`、`family_code`、`rule_family_code`、`room_code`）。
2. 邀请码正则、唯一约束、冲突重试、耗尽错误码均有测试。
3. 非成员访问任意家庭资源均返回 403 且不泄露资源名。
4. `state.snapshot` 中他人 `hand` 恒为空；暗杠 `tiles` 为空。
5. 关闭 `turn_timeout` 后 `deadline` 恒为 null；关闭 `ting_hint` 后 `tenpai` 为 `{}`。
6. 皮肤清单带 ETag，304 生效；缺图时前端回退 CSS。
7. WS `v=1` 客户端连接被 `BAD_VERSION` 拒绝（关闭码 4002）。
8. 注册：`ACCOUNT_ALLOW_REGISTER=false` 时接口返回 `ACCOUNT_REGISTER_DISABLED` 且账号服务零调用；开启后未发码直接提交返回 `VERIFY_CODE_REQUIRED`，验证码错误返回 `VERIFY_CODE_INVALID`，成功后可立即用新账号登录。
9. 找回口令：不存在的手机号发码仍返回 `{ok:true}`；正确验证码重置后旧口令登录失败、新口令登录成功；同一验证码二次提交返回 `VERIFY_CODE_INVALID`。
10. 验证码：60 秒内重复发码返回 `VERIFY_CODE_SEND_TOO_FAST`；同一账号连续 5 次错误后必须重新发码（`VERIFY_CODE_ATTEMPTS_EXCEEDED`）。
11. 安全：日志、审计、错误响应中 grep 不到 `passwd`、验证码明文与 `md5` 结果；`/api/auth/options` 与实际开关一致。
12. 观战：未选目标时 `hand=[]`、`spectate=null`；选定后仅 `spectate.target_seat` 的 `hand` 非空；同一 `loginID` 只占 1 个名额；切换后旧目标 `spectator_count` -1、新目标 +1；第 11 人返回 `SPECTATE_TARGET_FULL`；4×10 满后握手返回 `ROOM_SPECTATE_FULL`（4005）。
13. 观战者 `self_seat=null`、`legal.actions=[]`，任何座位操作返回 `NO_SEAT`；目标离座后收到 `event.spectate_changed{target_seat:null}` 且快照回到未选择态。
