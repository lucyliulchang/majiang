## 用户需求

基于现有家庭麻将系统（同一后端、同一数据库、同一账号体系），评估开发 Android 原生客户端的可行性，并产出一份结构完整、可直接执行的《可行性分析与开发计划》文档，最终落盘到 `plan/android家庭麻将客户端规划.md`，本次不涉及任何代码改动。

## 产品概述

现有系统已具备 PC 网页版与手机网页版，后端为服务端权威判定的在线麻将服务。Android 客户端的目标是让家人在手机上以「应用」形态完成 登录 → 大厅 → 开桌/凭邀请码进桌 → 横屏打牌 → 结算 → 战绩 的完整流程，并与网页端互通同桌。

## 已确认的方案约束

- 技术路线：**两阶段**。一期用 Capacitor/WebView 壳承载现有 H5 页面并补齐原生能力；二期把牌桌（最高频界面）用 Compose/Canvas 原生重写，其余页面继续复用 H5。
- 分发方式：家庭内直发 APK，不上架应用商店；App 启动检查版本并提示下载更新。
- 成本口径：以人日工作量 + 人民币区间呈现，不绑定具体团队规模。

## 核心内容要求

- 技术可行性：联机同步机制、性能表现、设备与系统兼容性，并明确与后端「零改动」的边界和必须改动项。
- 阶段划分与关键里程碑：每阶段目标、交付物、验收出口。
- 人员配置与资源投入：角色、最小配置与理想配置、真机与证书等资源。
- 时间与成本估算：人日区间、日历周期（兼职/全职两种换算）、费用区间。
- 测试方案与上线发布流程：协议契约、真机矩阵、弱网与断线重连、灰度与回滚。
- 主要风险与应对措施：风险等级、触发条件、缓解与兜底。

## 关键技术结论（文档需给出明确判断）

1. **可行，且后端协议零改动即可支撑一期壳客户端**：所需能力（HTTPS REST、WSS、JWT、快照重同步、动作幂等、座位保留）全部已具备。
2. **一期唯一必要的工程改动是「端点绝对化」**：`api/http.ts` 的 BASE 与 `ws.ts` 的 `location.host` 依赖同源，本地打包资源后必须改为构建期注入的绝对地址（`https://www.test.com/majiangapi`、`wss://www.test.com/majiangws`）；后端 CORS 默认 `*` 且使用 Bearer，不阻塞私有源。
3. **同步机制适配要点**：WebView 在前后台切换时 socket 可能被挂起，必须在 `onResume` 主动重连并 `state.resync`；服务端座位保留 180s，短暂切后台不丢座；不可依赖「推送到达」做状态累积，必须整份覆盖快照。
4. **性能判断**：服务端为权威判定且消息体小，单房 4–10 连接属轻载；客户端瓶颈在 WebView 首屏与音频解锁，不在同步；二期原生牌桌的收益主要在帧率、触控跟手与内存，而非网络。
5. **兼容性红线**：minSdk 建议 26（Android 8.0），WebView 内核需设最低版本门槛并在启动时检测（华为 HMS 设备内核与 Chrome 不同步，历史上 Chrome 78 曾导致整包白屏）；必须覆盖刘海/挖孔、手势导航、折叠屏与平板三种布局。
6. **分发**：不上架商店意味着放弃商店签名托管与自动更新，必须自建「版本清单 JSON + APK 直链 + 签名校验 + 应用内提示」链路，并接受「用户手动允许安装未知来源」的首次门槛。

## 估算方法（保证可执行）

- 工作量以「人日」为唯一单位，按功能点拆分到阶段，给出下限/上限区间（下限=熟练者顺路径，上限=含联调返工）。
- 一期壳（M1–M3）合计 20–30 人日；二期原生牌桌（M4–M6）合计 30–45 人日；总计 50–75 人日。
- 日历换算：兼职每周 8–12 小时约等于 1–1.5 人日/周；全职按 5 人日/周。给出两种日历区间，避免单一结论。
- 费用 = 人日 × 单价区间；同时给出「自有人力」的机会成本说明，不虚构外部报价。
